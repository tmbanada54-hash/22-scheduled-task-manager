Key Query — Scheduler (Hot Path)

Runs every 15-30s, uses partial index idx_tasks_next_run

SELECT id, name, payload
FROM tasks
WHERE status='active'
  AND is_enabled = TRUE
  AND next_run_at <= NOW()
ORDER BY priority DESC, next_run_at ASC
LIMIT 100
FOR UPDATE SKIP LOCKED;

Execution Lifecycle — With Retries

pending → running → success ✓ or failed ✗ → retry in 60s (×2 exponential) → pending (attempt 2) 
-- Retry chain via parent_execution_id
-- execution #1 (failed, attempt 1, is_retry=false)
--   └─► execution #2 (success, attempt 2, is_retry=true, parent=exec #1)

UPDATE executions SET status='failed', next_retry_at=NOW() + retry_delay * POWER(2, attempt-1) WHERE id=$1;
INSERT INTO executions (task_id, attempt_number, parent_execution_id, is_retry, triggered_by)
VALUES ($taskId, 2, $parentId, true, 'retry');

Historical prototype demo script

"Our database has two core tables: tasks — what to run and when — and executions — an immutable log of every attempt. The scheduler polls WHERE next_run_at <= NOW() using a partial index, so it's fast even with thousands of tasks. When a webhook fails, we mark the execution failed and schedule a retry with exponential backoff — delay × 2^(attempt-1) — linked via parent_execution_id so you can see the full chain in the UI. Views like v_task_stats power the dashboard without extra app logic."
